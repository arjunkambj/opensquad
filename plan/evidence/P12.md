### Review-pass verification — the activity-feed timezone fix

The one review-pass fix whose behaviour is pure arithmetic was executed rather
than reasoned about. The real `src/lib/date-ranges.ts` was imported into Node
25 (native type stripping) with the **process** timezone set to
`Asia/Kolkata` and the **workspace** zone passed as `America/New_York` — the
exact skew the finding describes. Verbatim:

```
$ TZ=Asia/Kolkata node check.mts
process TZ            : Asia/Calcutta
now, browser          : 16/09/2026, 09:00:00.000
now, workspace        : 15/09/2026, 23:30:00.000
todayInZone(ws)       : Tue Sep 15 2026
today from, in ws     : 15/09/2026, 00:00:00.000
today to,   in ws     : 15/09/2026, 23:59:59.999
7d from, in ws        : 09/09/2026, 00:00:00.000
7d to,   in ws        : 15/09/2026, 23:59:59.999
dst day from, in ws   : 01/11/2026, 00:00:00.000
dst day to,   in ws   : 01/11/2026, 23:59:59.999
dst day length hours  : 25
round trip            : Tue Sep 15 2026 -> Tue Sep 15 2026 Tue Sep 15 2026
bad zone falls back   : {"from":1789497000000,"to":1789583399999}
```

Read against the defect: the browser's calendar says 16 September while the
workspace's says 15 September, and the window sent is the **workspace's** 15
September, midnight to 23:59:59.999 in New York. Before the fix the same call
produced 16 September *Kolkata*, i.e. 15 September 14:30 – 16 September 14:30
New York, under a heading reading "Showing Sep 16". The heading now reads
"Showing Sep 15, 2026", which is the day the rows beneath it are stamped with.

The DST line is the second thing worth having: 1 November 2026 is New York's
fall-back day and the bound spans **25 hours**, because the end is derived
from the next local midnight rather than from a hardcoded 23:59:59.999. The
last line is the failure mode: an unreadable zone string returns a window
rather than throwing.

This is a one-off check run from the scratchpad, not a test file — no test
file was added, per `AGENTS.md`.

`npx tsc -p convex --noEmit` was deliberately **not** used as a signal — the
concurrent track owns `convex/`. It was observed failing once mid-card on
`convex/drafts.ts` (a circular-inference error in another track's in-flight
edit) which cascaded into `any` parameters across `src/`, including files this
card never touched. It cleared on its own within a minute. No file this card

### The runtime badge, answered directly

The question is whether anything keeps claiming "live" once the runtime is
gone, given that `getStatus().live` is a clock comparison computed **inside**
a Convex query and Convex re-runs queries on document change, not on time
passing. Three separate findings, two exercised and one not:

1. **EXERCISED — the client-side tick is real and it runs.** `window.setInterval`
   was wrapped on the page and `RuntimeBadge` forced to remount via in-app
   navigation. It registered a **15 000 ms** interval on mount, and over a
   measured 35 001 ms wait that interval **fired twice**:

   ```
   registered intervals (ms): [15000, 15000]
   ticks after 35001 ms      : { "15000": 2 }
   ```

   So the badge is not relying on the subscription to re-render it.

2. **Structural, not observed — the client can only degrade.** The live branch
   is gated on `status.live && (now - status.lastHeartbeatAt < 90_000)` with
   `now` coming from that tick (`RuntimeBadge.tsx`). A stale heartbeat flips
   `fresh` to false within one tick of the 90-second window closing and the
   badge falls through to "Runtime disconnected — Last heard from …". There is
   no path by which the client turns a backend `live: false` into "live".

3. **NOT EXERCISED — the transition itself was never watched.** `npx convex
   data runtimeConnections` returns **no row at all** for this workspace (four
   rows exist, all in P21's fixture workspaces, all `state:"connecting"` with
   no `lastHeartbeatAt`), so the badge is pinned on "Runtime never connected"
   and reads "No runtime has ever been connected to this workspace."
   **Blocker:** a worker heartbeating into a workspace this account is a member
   of. Until then the live → disconnected flip, the "connected, not signed in"
   branch and the `exists && !live` copy are all unexercised.

   What *is* measured is that there is nothing to degrade **elsewhere**: zero
   running CSS animations anywhere on the board (V08 step 6). So the failure
   mode ux.md J6 forbids — an animation still running after the runtime is
   gone — has no surface to occur on even if the badge were wrong.

21. **Zoned day boundaries are computed without a timezone database.** The
    conversion mirrors `localCivilToUtc` in `convex/lib/validators.ts`: guess
    the civil time as UTC, measure the zone's offset at the guess with `Intl`
    and correct, up to four iterations. Across a DST *gap* — a local midnight

    boundary instant rather than on a midnight, which is right for a range
    bound and worth knowing. A zone string `Intl` cannot read falls back to the
    browser's own midnight rather than throwing, so a corrupt

    down; it does **not** announce that it has done so.
