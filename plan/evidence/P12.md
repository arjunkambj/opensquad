## Contract changes

**`OverviewSearch` gained three members, all optional, all additive.** No
existing member changed its parser, and `BOARD_COLUMNS`, `ACTIVITY_RANGES`,
`OVERVIEW_DEFAULTS` and `overviewDefaults` keep their exported shapes.

- `tab?: "summary" | "prospects" | "decisions" | "receipts" | "comments"` —
  what `plan/ux.md` §2 already specifies for the detail route. Declared on the
  layout so the whole `/overview` subtree has one search definition.
- `from?: number`, `to?: number` — absolute epoch-millisecond instants, listed
  for `/overview` in ux.md §2 and required because `?range=custom` cannot
  otherwise be expressed. They bound `activity.list` only.

**Route shape.** `overview.tsx` is now a layout; `/overview` is unchanged as a
URL. `/overview/missions/$missionId` is new. Children read the search with
`useSearch({ from: "/_dashboard/_workspace/overview" })` — the id of the route
that declared `validateSearch`, never the leaf's own id.

**No backend contract changed.** `missions.listBoard`'s `visibility` argument
landed before this card, at `1f1c598`.

## V08–V11, step by step

Exercised by hand in the running app (`npx vite --port 5173`) against the
shared dev Convex deployment, signed in as the repository owner's own account.
A workspace named *P12 Verification Workspace* was created through the normal
onboarding flow, with a business profile pointing at `https://example.com`, one
campaign (*P12 board verification campaign*) whose Apollo source plan was
confirmed, and missions created through the board's own New-mission dialog.
No mail was sent and no external provider call was made: `missions.create`
dispatches `devFixtureMissionWorkflow`, which parks on a fixture decision.

### V08 — Board truth, counts and independent sales state

1. **Missions created through their real supported action.** Two missions were
   created from the board dialog. Observed live, in this order: the card
   appeared in **Needs you** with state chip **Running** and progress
   "Fixture scan complete — 2 prospect branches" (this is `active` with
   `requiredDecisionCount > 0` — the pull-in that makes Needs you five states
   wide), then within seconds the chip became **Waiting on you** and the
   progress "Waiting on a required decision".
2. **Column mapping, against the declared table.** Final observed board:
   Backlog `1` holding *mission A* with chip **Cancelled**; Needs you `1`
   holding *mission B* with chip **Waiting on you**; In flight `0`; Done `0`.
   That is the spec's mapping directly: `cancelled` sits in Backlog with its
   own badge and is never a completion, and a decision-blocked mission sits in
   Needs you. **Not reached:** a `completed` mission in Done and an `active`
   mission with no open ask in In flight — both need a connected runtime, and
   none exists (see *Honest deferrals* 4).
3. **Card fields, checked against the record.** Title, state chip, owner
   (`Scout`, joined from `employees.list`), current step (`progressSummary`,
   the backend's string, never synthesised), the explicit decision count —
   "1 ask open" then "no asks open" after cancellation, rendered as words and
   never hidden — and freshness ("updated just now" → "updated 1 minute ago").
4. **Failure does not pose as an approval.** No `failed` mission could be
   produced without a runtime, so this was verified by construction rather
   than observation: `boardColumn` is a stored field, `MISSION_STATE_BOARD.failed`
   is `needs_you`, the board never recomputes a card's column, and a `failure`
   block renders as a destructive-toned technical error offering Archive and
   the run receipt. No code path in this card constructs a retry. Recorded as
   **not observed** in *Honest deferrals* 4.
5. **No animation anywhere.** There is no per-mission execution signal —
   `vRuntimeStatus` exposes no `currentRunId`, and `state === "active"` is not
   one. The board carries exactly one liveness surface, the workspace runtime
   badge, and zero pulses, dots or progress lines.

### V09 — Deep links, filters, archive and reload

1. **Filter, open, copy, reload.** Selecting the campaign wrote
   `/overview?campaign=j97afc…`. Opening the card gave
   `/overview/missions/k978da…?campaign=j97afc…` — the filter travels into the
   detail URL. Navigating to
   `/overview/missions/k978da…?campaign=j97afc…&tab=decisions` from a cold load
   restored the same record **and** the same tab.
2. **Closing preserves the board context.** From
   `/overview/missions/k978da…?tab=comments`, Escape produced `/overview` (the
   detail's own `?tab` dropped, nothing else touched). From
   `/overview/missions/k978da…?campaign=j97afc…`, Escape produced
   `/overview?campaign=j97afc…` — the campaign filter intact. This is
   structural, not hand-maintained: the filters live on the parent route, so
   there is no filter state that *can* be lost.
3. **The date filter cannot hide unfinished work.** The receipts feed's range
   is bound to `activity.list` only. `missions.listBoard` takes no date
   argument and is not passed one; with the feed showing an empty "Today"
   window, both board cards stayed on screen.
4. **Archive and restore.** Cancel → version 4→6, chip **Cancelled**, action
   group correctly reduced to Archive alone. Archive → version 7, an
   **Archived** chip added, action group replaced by "Restore to the board",
   and **state and outcome unchanged** — archive claimed nothing about
   success. The card left the board (Backlog `1`→`0`). Restore → version 8,
   card back in Backlog. Round-tripped twice.
5. **Missing or unauthorized record URL.** `/overview/missions/k978…25t` (one
   character changed). **Before `cb6da80`:** "This page didn't load" plus the
   raw string `ArgumentValidationError: … Validator: v.id("missions")` and a
   request id. Convex ids carry a checksum, so a mistyped id fails *argument*
   validation and never reaches the handler's `NOT_FOUND`, leaving it with no
   domain code for the boundary to read. **After:** the in-shell "Not found"
   state — "That link doesn't name a record in this workspace…" — with the way
   back. `/overview?campaign=notacampaignid` renders the same safe state.

### V10 — Mobile, keyboard and accessible state changes

1. **375 × 812.** `/overview`: `document.documentElement.scrollWidth` equals
   `clientWidth` (375) — no horizontal page scroll. The board is a **column
   selector** with all four names and all four counts visible
   (`Backlog 1 · Needs you 0 · In flight 0 · Done 0`) and one column's cards
   below it; the four columns never collapse to fewer than four states.
   Tapping *Backlog* wrote `?column=backlog`, still with zero overflow. Mission
   detail at the same width: no page overflow, tabs scroll inside their own
   container, no clipped body text. At 1024px the board is 2×2 (`md:grid-cols-2`)
   and at ≥1280px it is 4-up.
2. **Keyboard, measured.** With focus in the 4000-character note textarea:
   sidebar `data-state` was `expanded` before ⌘B and `expanded` after;
   `document.querySelectorAll('[role="dialog"]').length` was `0` before ⌘K and
   `0` after; the typed text was intact. With focus on the detail heading
   instead, ⌘B moved the sidebar `expanded → collapsed → expanded` — the guard
   narrows the shortcut without removing it. **Before this card both shortcuts
   fired regardless of focus.**
3. **Focus move-in and restore.** Opening a card left
   `document.activeElement` as `H1` (the mission title, `tabIndex={-1}`, not a
   trap). Pressing Escape navigated to the board and left `document.activeElement`
   as the `A` element whose text begins "Board verification mission A" — focus
   returned to the row that opened it, tracked by mission id rather than by a
   DOM reference.
4. **State without colour.** Every chip carries the word: Running, Waiting on
   you, Waiting on the runtime, Paused, Failed, Completed, Cancelled, Queued,
   High priority, Archived. The runtime badge reads "Runtime never connected",
   "Runtime disconnected", "Runtime connected, not signed in" or "Runtime
   live". Tints are a redundant second signal.
5. **Destructive controls say what they do.** Cancel's confirmation: "Every
   open ask is retired, child work is cancelled and in-flight runs are swept.
   This cannot be undone … mail already accepted by the provider cannot be
   recalled." Archive's: "Archive hides it from the board. It does not claim
   the work succeeded…". Both observed in the dialog.
6. **Screen-reader noise removed.** `ui/command.tsx` rendered
   `DialogHeader/Title/Description` as a **sibling** of `DialogContent`, and
   `CommandDialog` is mounted inline in the sidebar tree — so "Search" and
   "Jump to a page in OpenSquad." sat permanently in the nav's DOM on every
   page. Moved inside `DialogContent`.

### V11 — Empty, loading, offline, stale and error states

1. **A new workspace with nothing in it.** All four columns rendered `0` with
   their own copy naming what will fill them — Backlog "A confirmed mission
   waits here before it runs. New mission puts one here."; Needs you the *good*
   empty, "Nothing is waiting on you", with no action attached. The attention
   block read `0` with "Nothing is waiting on you.", and the feed read "No
   activity in Sep 15, 2026" with the line that work in progress is on the
   board above and is never hidden by the date range.
2. **Loading does not look like completed-empty work.** A `MutationObserver`
   over an in-app navigation from `/decisions` to `/overview` captured the
   loading frame: all four headers rendered `Backlog —`, `Needs you —`,
   `In flight —`, `Done —` alongside "Loading Backlog" / "Loading Needs you"
   panels. Never `0`.
3. **Two sessions, stale version, resolved in place.** Two tabs held the same
   mission at version 8. Archiving in tab A took it to version 9. Tab B's
   entire action group was **replaced in place** by: "This mission changed
   while you had it open — it is now version 9, not 8. Load it before acting,
   so you are acting on what is actually here." with a *Load the current
   version* control. Not a toast, not a disabled button, not a silent
   overwrite. Pressing it restored the action group with the correct action for
   the current state ("Restore to the board").
4. **Counts that cannot be invented.** The attention block's *Unassigned mail*
   and *Overdue next actions* slots render "Not available yet" with the reason,
   and **no number** — the distinction between "we asked and nothing is
   waiting" (`0`) and "we cannot ask" is the point of the shape.
5. **One number, one query.** The sidebar's Decisions badge and the attention
   block read the same call through one hook with identical arguments. Observed
   together at `0`, then both at `1` after a mission opened its required ask,
   then both back at `0`. Outside the workspace gate (during onboarding, before
   a workspace existed) the query is skipped and **no badge renders** rather
   than a `0` claiming an empty queue — observed on the setup screen.
6. **Absent is unknown.** A run receipt with no reported usage renders
   "unavailable — the runtime reported none", never `0`, and no number is
   labelled as currency or credits.

## Backend gaps for the integrator

1. **BLOCKER — the deployed `missions.listBoard` has no `visibility`
   argument.** `convex/missions.ts` in the working tree does (landed at
   `1f1c598`), and `convex/_generated` is consistent with it, so the client
   typechecks and builds. The **running dev deployment** is behind. Clicking
   *Show the archive* produced, verbatim:

   ```
   [CONVEX Q(missions:listBoard)] Server Error ArgumentValidationError:
   Object contains extra field `visibility` that is not in the validator.
   Object: {column: "backlog", limit: 25.0, visibility: "archived", …}
   Validator: v.object({campaignId: …, column: …, cursor: …, limit: …,

   ```

   No convex CLI command was permitted to this track, so this could not be
   fixed here. **Whoever next pushes the deployment closes it**; nothing in
   `src/` needs to change. Until then `?archived=true` fails at runtime — it
   fails safely, in-shell, with a retry, but it fails. Archive and restore
   themselves were both proved end to end through the detail route, which uses
   `missions.get` and has no visibility gate.
2. **`runs.listForEmployee` (ux.md gap (d)) was NOT written.** ux.md assigns it
   to P12, but it is a `convex/` change and `convex/` belonged to P11 this
   wave, so it was reported rather than edited. It is args-and-handler only
   over the existing, entirely unused `by_employeeId_and_state` index. **One
   safety note for whoever writes it:** that index carries no `workspaceId`, so
   the handler must load the employee and check
   `employee.workspaceId === args.workspaceId` before querying, or a foreign
   `employeeId` leaks another workspace's runs. `/employees` is not a P12
   screen and `deriveEmployeeStatus` already returns an honest
   `disconnected`/`idle` with no run data, so nothing animates in its absence.
3. **`drafts.listForMission` and `missions.get().prospects` truncate
   silently.** Both use `take(limit)` with no `hasMore`, so the UI cannot know
   whether it is showing everything. Both sections are labelled "up to 50" and

4. **`listBoard` returns the whole mission document**, `inputSnapshot`
   included — bounded only at 64 KiB per row. Four columns × 25 rows is a

5. **Confirmation wanted** that the two unavailable attention slots stay

## Honest deferrals — what the above does NOT prove

1. **`j`/`k` + Enter row navigation was not built.** `plan/ux.md` §6 scopes
   roving-key navigation to `/decisions` and `/inbox`, "where the whole job is
   working a queue" — not to a four-column board, where arrow and letter keys
   would also have to avoid hijacking scrolling when focus is outside a column.
   Accepted limit, per the brief, not chased. Every card is a focusable link,
   so the board is fully workable with Tab and Enter.
2. **The ≥1280px list-beside-detail split was not built.** Opening a mission
   replaces the board at every width, with a back control at every width. The
   nesting done in `64cf7a6` is exactly what makes the split a later CSS
   decision inside `overview.tsx` rather than a route change, so deferring it
   costs nothing structurally.
3. **`/` to focus a list search is N/A rather than deferred** — ux.md scopes it
   to `/leads` and `/inbox`, and `/overview` has no text search.
4. **Four mission states were never observed on screen.** `queued`, `active`
   with no open ask, `completed` and `failed` all need a connected runtime, and
   this workspace has none ("Runtime never connected"). The dev fixture
   workflow parks on a required decision, so what was observed was
   `active → waiting_for_user → cancelled`. In flight and Done were therefore
   only ever seen empty, and the failure treatment and the "no Retry" rule were
   verified by reading the code, not by watching a mission fail. **Whoever
   runs the acceptance gate with a live runtime should re-check V08 steps 1–3
   against a real `completed` and a real `failed` mission.**
5. **The runtime badge's degradation tick was never observed degrading.** With
   no runtime ever connected the badge is pinned on its first state. The
   fifteen-second tick, the 90-second window and the "connected, not signed in"
   branch are unexercised. The important property — that the client can only
   ever *degrade* the backend's `live` verdict, never upgrade it — is
   structural (`live = status.live && freshHeartbeat`), but it has not been
   watched flipping.
6. **Column paging was never exercised with a second page.** Two missions is
   not 26. "Show more", the expanded view's Next/First page controls and the
   "page 2" header were never rendered against real data. The empty-behind-a-
   cursor state likewise.
7. **The viewer role was never exercised.** The verification account is the
   workspace owner. `PermissionNote` in place of the lifecycle group, in place
   of the comment form, and in place of New mission are all unobserved.
   V23 step 2's server-side backstop is unaffected either way.
8. **Offline and reconnect (V11 step 2) were not exercised.** No network
   throttling or disconnection was performed, and the worker could not be
   disconnected because none was connected.
9. **`?archived=true` fails against the current deployment**, per *Backend
   gaps* 1. The archived-board listing, its empty state and its "Back to the
   board" control are unverified at runtime.
10. **Bounded counts read `25+`, not `50+`.** ux.md's example is `50+`, which
    would require `limit: 50` per column. `listBoard` returns the full mission
    document including `inputSnapshot`, so four columns × 50 rows is a worst
    case in megabytes; `25+` from a 25-row page is honest and a hard-coded
    `50+` from a 25-row page is not. A deliberate deviation from the
    illustrative number, not from the rule.
11. **Six things `plan/ux.md` asks for are omitted with the reason on screen,**
    because no query serves them: the unassigned/takeover count (no
    `convex/conversations.ts` at the time this was written), the overdue

    (no per-card query exists — prospect branches render on the detail tab
    instead), a link from a prospect branch to a lead (`/leads/$prospectId`
    does not exist and `missionProspects.prospectId` is a bounded string, not
    an `Id<"prospects">`), research evidence on mission detail (the `evidence`
