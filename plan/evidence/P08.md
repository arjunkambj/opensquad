## API surface consumed (all pre-existing P02)

| UI surface | Calls |
|---|---|
| Onboarding | `workspaces.ensureWorkspace`, `workspaces.getCurrent`, `businessProfiles.get`/`update` (`expectedVersion`, 0=create), `workspaces.update` (`expectedPolicyVersion` on timezone change), `workspaces.setSendingPolicy`, `campaigns.create` (`requestId` idempotency), `campaigns.confirmSourcePlan` (`expectedBriefVersion`), `campaigns.setState` (activate the confirmed campaign), `workspaces.setAutomationState` (activate after confirm) |
| Employees | `employees.list`, `employees.update` (`expectedInstructionVersion`) |

Contract notes honored:
- `workspaces.update` gets the **current** `policyVersion` whenever a timezone
  change is possible; a real change bumps it atomically. In onboarding the
  send-policy save uses the version **returned** by `workspaces.update`, so the
  pair composes. CONFLICT anywhere → inline "changed elsewhere, latest values
  loaded" + resync-on-`updatedAt` (name-only/enabled edits don't bump versions,
  so `updatedAt` is the sync signal).
- The workspace stays `paused`/`onboarding_pending` until the review step's
  explicit checkbox + confirm: `campaigns.create` → `confirmSourcePlan` →
  `setAutomationState("active")`, in that order. `create` is keyed by a
  `crypto.randomUUID()` `requestId` per wizard session; if a replayed create
  returns a draft whose stored scope no longer matches the form (edit between
  retries), a fresh `requestId` is minted instead of confirming stale scope.
  An "already confirmed" CONFLICT on retry is treated as idempotent success.
- Only **Apollo** is offered as a source — `ENABLED_SOURCES=["apollo"]`; the
  UI copy says YC/TrustMRR are pending their extraction gates.
- 2026-09-15 correction: this originally left the campaign in `draft` and
  assigned activation to P09. Nothing in the product ever moved it out of
  `draft`, and `missions.create` rejects a draft campaign, so no work could
  start. The wizard now calls `campaigns.setState` after `confirmSourcePlan`
  and before `setAutomationState`. Pipeline execution remains P21's and
  Apollo sourcing P09's; neither touches campaign status.
- Employee status is derived only from `enabled` + runtime availability;
  `idle`/`busy`/`blocked` stay unreachable until real run/connection state
  exists (P06 `runs`, P07 `runtimeConnections`). Enabled employees truthfully
  show **Disconnected**; `allowedCapabilities` render as read-only labels.
- Integrations section shows honest PENDING/BACKEND-MANAGED states with
  disabled controls — no simulated connect. Workspace/Sending/Automation/
  Members are working controls; copy distinguishes the two.
