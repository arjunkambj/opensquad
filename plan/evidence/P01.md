## Hexclave project — usable, with a recorded limitation

`@hexclave/react@1.0.121`'s `getConvexProvidersConfig` emits two `customJwt`
providers: the users issuer `https://api.hexclave.com/api/v1/projects/{id}` and
an anonymous-users issuer, both ES256 against the project JWKS (verified live:
200, 2 keys). Per Convex docs, `customJwt` without `applicationID` does not
verify `aud`; security is carried by the exact `iss` match, which already
embeds the project ID — so tokens from other Hexclave projects cannot verify.
`tokenIdentifier` will be `iss|sub` with `sub` the Hexclave user ID; `sub`,
`iss`, `exp`, `iat`, `kid`, `alg`, `typ` are the contract fields.

The frontend login path is wired end to end: `HexclaveClientApp` (cookie token
store, `/handler`, `/sign-in`, post-auth `/overview`), `HexclaveHandler` route,
magic-link + Google OAuth form, and `convex.setAuth(hexclaveClientApp.getConvexClientAuth())`
which supplies the session access-token JWT to the client.

Limitation (not a pass): no human completed a live sign-in, so no real JWT was
decoded — the audience value and the actual identity-claim surface
(`email`, `name`, `selected_team_id`, …) are asserted from the provider
config, not from an observed token. A human sign-in check is required for
V01 step 3 / V02; P02 must build authorization on `ctx.auth.getUserIdentity()`
claims, never browser-supplied identity.
