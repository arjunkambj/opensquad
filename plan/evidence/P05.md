## Inspection findings — installed `@agentmail/convex@0.1.0`

Exports verified against `dist/` (not just docs):

- Root (`.`) exports `AgentMail` class, `vOutboundId`, `vEvent`,
  `vEventType`, `vOutboundStatus`, `vSendKind`, `toSendPayload`,
  `verifyAgentMailWebhook`, `WebhookVerificationError`, and the
  `SendArgs`/`ReplyArgs`/`ForwardArgs`/`AgentMailEvent` types.
- `./convex.config` exports `defineComponent("agentmail")` which itself
  `.use()`s `@convex-dev/workpool` twice: `sendPool` and `callbackPool`
  (installed as `agentmail/sendPool`, `agentmail/callbackPool` on push).
- `AgentMail` constructor: `(component: ComponentApi, options?)` with
  `webhookSecret` (default `process.env.AGENTMAIL_WEBHOOK_SECRET`),
  `initialBackoffMs` (30 000), `retryAttempts` (5), `onEvent`, and
  `onMessageReceived` mutation `FunctionReference`s. Credentials are read
  from deployment env inside component functions — never through args.
- `handleWebhook(ctx: { runMutation }, req: Request)` reads the RAW body,
  verifies `svix-id`/`svix-timestamp`/`svix-signature` via `svix`'s
  `Webhook.verify` (throws → 401 "invalid signature"), then runs component
  mutation `lib.handleEvent` and returns 204. Without a configured secret it
  throws before touching state.
- `lib.handleEvent` dedupes by `event_id` (`events.by_eventId`), persists
  `message.received` bodies into `inboundMessages`, projects delivery events
  onto `outboundMessages` by `agentmailMessageId`, then enqueues `onEvent` /
  `onMessageReceived` via `callbackPool` — callback failure cannot block
  ingest, and ingest commits before callbacks run.
- SEND SURFACE (the reason the narrow adapter exists, G3 confirmed):
  `sendMessage`/`replyToMessage`/`forwardMessage` → `enqueueSend` mutation →
  `sendPool` Workpool action `performSend` with retry
  `{maxAttempts: retryAttempts(5), initialBackoffMs(30s), base: 2}`.
  `agentmailFetch` sets only `Authorization`/`Content-Type` — **no
  `Idempotency-Key` header** — and treats 400/401/404/405/410/413/414/415/422
  as permanent, everything else transient→retried. `cancelSend` only marks a
  `pending` row `failed`; it cannot retract an HTTP request already in
  flight. Component endpoints: `/inboxes/{id}/messages/send`,
  `/messages/{parent}/reply|reply-all|forward`, base
  `https://api.agentmail.to/v0` (override `AGENTMAIL_BASE_URL`).
- `outboundMessages` finalized rows are swept after 7 days — but only if the
  app schedules `cleanupFinalizedOutbound`; the component ships no cron.
  OpenSquad never depends on that store for audit history (G3).
- **Type skew found (P05 fix):** component `RunMutationCtx.runMutation`
  (resolved under convex 1.45.0) expects the
  `(mutation, args, options?: {transactionLimits})` signature, while the
  http-action ctx exposes the single-argument `OptionalRestArgs` form.
  `convex/http.ts` adapts `{ runMutation }` positionally — verified the
  component only calls `runMutation(mutation, argsObject)` — rather than
  casting the whole ctx. Flag for future component upgrades.

## Reconciliation contract implemented

- `executeSendAttempt({inboxId, idempotencyKey, payload})` — internalAction,
  exactly one POST `…/inboxes/{id}/messages/send`, `Idempotency-Key` header,
  outcome `accepted | rejected | uncertain` with sanitized provider detail
  (error bodies truncated to 1024 chars; accepted bodies must carry
  non-empty `message_id`/`thread_id` else `uncertain`).
- `reconcileSendAttempt` — same transport, distinctly named for audit: legal
  only for a still-`uncertain` attempt inside the provider's verified
  idempotency window (documented 24 h — confirm by probe) after full
  re-validation; replay may itself deliver mail; never mint a fresh key.
- Reply-in-thread uses the same contract against
  `/inboxes/{id}/messages/{message_id}/reply` — P10/P11 extension, not in
  this spike.
- `diagnosticSendProbe` — internal-only dev probe for the blocked live gate.
  **TODO(P16): remove before public release.** Task-card wording "remove any
  temporary probe sending capability before merging" reconciles with the
  dispatcher's explicit instruction to keep it internal-only and marked: it
  is unreachable from clients/HTTP, so no public send path exists — but the
  integrator should delete it at/before P16 regardless.

### Provider behavior deltas vs docs

- `message_id` is the RFC 5322 Message-ID (`<…@email.amazonses.com>`), not a
  slug — path parameters MUST be URL-encoded.
- `thread_id` is PER-INBOX: the same message has `c97d74a5…` on the sender
  side and `799f78e4…` on the recipient side. P11 must key conversations by
  (inboxId, threadId), not threadId alone.
- Inbox re-create with an existing `client_id` returns 200 + the existing
  inbox (not an error) — safe to call at provisioning time.
- Provider idempotency on replay is total: the replayed request produced no
  second `message.sent` webhook event, not just no second delivery.

### Cross-workspace / unmapped inbox state today (item 8)

Workspace mapping tables are P10/P11 and do not exist. Today the component
persists `inboundMessages` for EVERY inbox the org-wide webhook delivers
(both probe inboxes are unmapped) and the app stubs only log provider IDs —
there is no quarantine, no unknown-inbox rejection and no sales-side dedupe
record. P11 contract must add: inbox→workspace resolution from a saved
assignment, quarantine for unknown inboxes, app-level dedupe by
(inboxId, messageId) as well as eventId, and a small replay/failure record
(`mailEvents` table suggested above).
