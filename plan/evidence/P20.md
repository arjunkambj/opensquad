## Contract decisions where §4.3 left a choice

1. **`leadEvents.kind` is a closed union of 12 members**, not the bounded
   string `activityEvents.kind` uses. §4.3 names categories, not literals; the
   P20 card explicitly asks for "the `leadEvents` kind/actor unions", and a
   lead event is the audit record that proves a human stage correction or a
   booking transition — it is not a receipts feed. Members:
   `stage_changed`, `owner_assigned`, `note_added`, `next_action_set`,
   `next_action_cleared`, `research_applied`, `contact_enriched`,
   `booking_proposed`, `booking_confirmed`, `booking_rescheduled`,
   `booking_cancelled`, `booking_outcome_recorded`. **If P19 or P21 needs a
   thirteenth, widen it here — do not add a parallel string.**
2. **`leadEvents.actor` is a discriminated union**
   (`{source:"human",identityKey}` | `{source:"workflow"}` |
   `{source:"system"}`), deliberately unlike `activityEvents.actor`'s bare
   string. §4.3 says the actor comes from auth or the internal workflow; the
   union makes that structural — only a human actor can carry an identityKey.
   The originating run stays in the top-level `runId?`.
3. **`confirmationSource` declares both `manual` and `provider`, and
   `ENABLED_CONFIRMATION_SOURCES = ["manual"]` gates the write.** This mirrors
   the repo's own `ENABLED_SOURCES = ["apollo"]` precedent for
   declared-but-gated vocabulary. P19 must refuse `provider` until a validated
   calendar connector verifies the event. Declaring only `manual` was the
   alternative; it was rejected because it forces a schema edit to the table
   P20 exists to declare once.
4. **`nextAction.kind` is a closed 8-member union** (`follow_up_email`, `call`,
   `await_reply`, `research`, `enrich_contact`, `propose_booking`,
   `confirm_booking`, `review`). §4.3 says "action kind" and enumerates
   nothing anywhere in the plan — this vocabulary is derived from the §5 CRM
   and booking entry points and the §8.7 transitions, and is the weakest-sourced
   decision in this card. P19 should widen it here if its picker needs more.
5. **`contact.providerEmailStatus` is `verified|guessed|unavailable|unknown`**,
   not the worker's `emailConfidence: high|medium|low`. §4.3 demands a
   *provider status* kept distinct from OpenSquad send eligibility;
   confidence bands cannot express "the provider says no address exists".
   `assertProspectContact` refuses `verified` with no address and refuses
   `unavailable` with one. Per §4.5 the worker vocabulary stays a wire shape and
   does not become the application validator — P09 maps between them.
6. **`sourceRefs[].source` reuses the §4.1 `apollo|yc|trustmrr` vocabulary.**
   §4.5 `discover` accepts confirmed sources only, so no `manual` member was
   invented. Manual lead entry would be a deliberate widening here.
7. **Observed metric metadata is a typed object** (`name`, `value`,
   `currency?`, `period?`) modelled on the §4.1 TrustMRR triple, not a
   key/value bag (AGENTS.md forbids loose dictionaries). `currency`/`period`
   are optional so a non-revenue metric is not forced to invent them.
8. **`bookings.timezone` and a `slots` proposal's `timezone` are independent.**
   The row-level field is the confirmed meeting's zone; the proposal's records
   what was offered. §8.7 requires a reschedule to preserve previous and new
   values, which a single promoted copy would destroy.
9. **`sourceRefs` distinctness** is keyed on `(source, providerRecordId)`,
   falling back to the normalized `profileUrl` when the provider exposes no ID.
   `assertSourceRefs` drops duplicates (so re-discovery merges instead of
   consuming one of the ten slots) and only then enforces the cap of 10.

## Deliberate additions beyond the card's literal field list

  existing `draftFields`. `plan/architecture.md` §4.3 (the paragraph beginning

  card says to reuse "the existing … version helpers"; there is no importable
  one. `convex/missions.ts:98` has a module-local, mission-typed

  lines. The new export matches their `CONFLICT "<field> version is N, not M"`
  message shape. **Those two existing call sites were NOT migrated** — that is
  another card's file scope.

## Honest deferrals — what the checks above do NOT prove

Compiling is not evidence that anything works. Specifically:

1. **The schema was never pushed.** `npx convex dev/push/deploy` was outside
   this card's permitted commands, so Convex's *server-side* schema validation
   never saw these definitions. Not verified by any check here: that the search
   index is accepted, that the index-name lengths and counts pass the backend's
   limits, or that `defineSchema` accepts this table set against an existing
   deployment's data. The longest new name,
   `by_workspaceId_and_ownerIdentityKey_and_nextActionDueAt`, is 55 characters,
   under the 64-character limit that already forced a rename on `missions` —
   that is arithmetic, not a push receipt. **The first agent to run
   `convex dev` against a P20 branch should record the push in its own
   evidence.**
2. **No row was ever written or read.** Every validator and helper here is
   unexercised: `normalizeCanonicalDomain`, `assertSourceRefs`,
   `assertProspectContact`, `assertBookingProposal` and `assertBookingTimes`
   have no caller yet and no probe was run against them. They typecheck; they
   are not tested. Per AGENTS.md this project writes no tests, so P19/P21's
   live probes are the first real exercise.
3. **`normalizeCanonicalDomain` is not public-suffix aware.** §4.3 asks for "a
   real URL/public-suffix-aware approach". What shipped extracts the host
   through the URL parser (so IDN is punycoded and paths cannot leak into the
   dedupe key), lowercases, drops a trailing root dot and drops a leading
   `www.`, then applies the existing dotted-domain syntax floor. Every other
   subdomain is preserved, which satisfies "preserve meaningful subdomains",
   and no bundled suffix list exists, so a registrable base cannot be computed.
   `a.co.uk` and `b.co.uk` stay distinct (correct); `shop.acme.com` and
   `acme.com` also stay distinct (intended, per §4.3, but worth knowing).
   **P09 owns Apollo dedupe and should deepen this function in place** rather
   than adding a second normalizer.
4. **`nextAction.kind` and `leadEvents.kind` member lists are derived, not
   specified.** No plan document enumerates either. They are closed unions on
   purpose, and widening one is a one-line edit at this single site — but the
   first consumer may well need to widen them.
5. **`DRAFT_EVIDENCE_MAX_ITEMS = 25` (validators.ts) is looser than §4.5's
   12-observation research cap.** Not reconciled here; it belongs to the draft
   path, not the evidence table. Flagged for P21.
6. **`decisionFields`' forward-reference comment is still stale** — it says
   those fields become `v.id(...)` "when P10/P11 land their tables", and all
   three tables have landed. Left as found because editing it from this card
   would pre-empt P11.
