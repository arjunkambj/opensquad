### Why REST, not MCP

Headless Convex actions cannot complete browser OAuth. The documented
server-side path is an API key in `x-api-key` / `X-Api-Key`. The three
REST operations the MCP tools wrap are the closed allowlist:

| Method | Path | Credits | Use |
| --- | --- | --- | --- |
| POST | `/mixed_companies/search` | 1 / page | company discovery |
| POST | `/mixed_people/api_search` | 0 | people search, no emails |
| POST | `/people/match` | billed | one-person enrichment |

`/people/match` always sends `reveal_personal_emails=false` and
`reveal_phone_number=false`. `webhook_url` is never sent. Email send,
sequences, enrollment, tasks, contact writes, personal-email reveal,
phone reveal, waterfall enrichment, bulk enrichment and any unknown path
are not callable from this adapter.

Auth: `process.env.APOLLO_API_KEY`. Optional `APOLLO_BASE_URL` defaults
to `https://api.apollo.io/api/v1`.

### Reservations and honesty

- Company search: `beginApolloOperation` reserves `research_searches`
  (`scopeKey campaign:<campaignId>`, `periodKey lifetime`, limit 5).
  Duplicate `operationKey` with the same digest replays; a different
  digest is CONFLICT. Missing `APOLLO_API_KEY` is a release (never
  contacts the provider). 2xx commits. Transport/timeout with no HTTP
  response releases. 401 releases (unauthenticated, no search). Other
  HTTP statuses after the request left Convex are `markUncertain`.
- People search: a `providerOperations` row with **no** usage
  reservation (0 credits).
- Enrichment: `apollo_enrichments` against `campaign.enrichmentLimit`.
  Allowance exhaustion returns `unavailable` without calling the
  provider. 2xx with a person object commits even when no email is
  returned.
- No email is synthesized. `providerEmailStatus: "verified"` is refused
  without a provider-returned `person.email`. `personal_emails[]` is
  ignored. G2 item 5 is still enforced in `applyContactEnrichment`
  (qualified + at least one evidence row) and in
  `prepareContactEnrichment` before the people search.

Stored `resultRef` is a sanitized inline object: candidates
(name/domain/id/url/sourceRefs/fitReason) or a contact or people
(id/name/title/domain). No phones, no personal emails, no API key, no
raw provider dump.
