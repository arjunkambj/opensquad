`conversationFields`, all optional so an inbound row is creatable without them:

## The reply workflow's shape

```
ingest step 5  ─or─  conversations.resume
        │  (both keyed on incoming:<inbox>:<message> — at most one mission ever)
        ▼
  missions row  kind:"reply", parentMissionId = the outreach mission,
                campaignId frozen at association, inputSnapshot built the way
                missions.create builds one
        │  start(..., startAsync: true) ENQUEUES; it does not run inline
        ▼
1. gateMission                     queued→active; paused parks on resumeEvent
2. classifyReplyStage              re-runs the whole gate, pre-checks the runtime,
                                   reads the body back through the component,
                                   dispatches operation "classify_reply"
        │  awaitEvent(worker completion) — durable, holds nothing
3. applyReplyDisposition           re-reads the workerRequests row (the event was
                                   a hint), maps through
                                   replyDispositionFromClassification
        ├── "stop"    → completeReplyMission with a stated outcome
        └── "propose" ▼
4. proposeReplyDraftStage          gate again, resolves the recipient BEFORE
                                   spending, dispatches operation "draft"
        │  awaitEvent(worker completion)
5. installReplyDraft               gate a third time, then
                                   internal.drafts.createRevision → the ordinary
                                   required `draft_approval` ask, read back and
                                   asserted present
6. markAwaitingUser                mission reads "Needs you"
        │  awaitEvent(decision continuation) — the durable human wait
7. checkContinuation               re-validates version + generation
        ├── approved          ▼
        ├── changes_requested → back to 4 with the reviewer's comment (once)
        └── rejected          → completeReplyMission("skipped")
8. checkApprovedSend               a PURE READ of the attempt rows for the
   (loop, ≤14 waits)               approved revision — it dispatches nothing
        ├── wait     → step.sleep until the parked attempt's nextPermittedAt
        ├── review   → markAwaitingUser + awaitEvent(delivery_uncertain ask)
        └── settled  → completeReplyMission with what actually happened
```

**Step 8 is why the mission does not end at approval.**
`sending.evaluateSendGates` refuses a mission that is `completed` with
`mission_inactive`, and the mission it reads is this one — `loadAttemptContext`
resolves it from `draft.missionId`, which `installReplyDraft` sets to the reply
mission. `beginDispatch` runs that gate on every re-entry and, on a block,
patches the attempt to `cancelled`. So a workspace whose send window had closed
parked the attempt with a wake for the next opening, the workflow completed the
mission seconds later, and the next morning's wake threw away the reviewer's
approved reply. The same terminal mission made `sending.openDeliveryUncertainAsk`
return `{opened: false}`, so a lost acknowledgement would have opened no
reconcile ask at all.

Two durable waits, neither holding anything. The workspace execution slot is
acquired by the **worker** at `/worker/claim` and released when its request
reaches a terminal state; by the time the workflow parks on a human its worker
request is already terminal, the mission has left `waiting_for_runtime`, and the
wait costs one journal row. A missing runtime connection parks on `step.sleep`
(≤10 × 60 s) and retries rather than failing the mission.

**No auto-send path exists.** `convex/workflows/reply.ts` contains no call to
`sending.*`, none to the component's `sendMessage`/`replyToMessage`/
`forwardMessage`, and does not start `sendDraftWorkflow`. The only transition
from a draft to the wire is `approvals.approve`, an editor-authenticated human
mutation, which itself only schedules `internal.sending.sendApprovedDraft` — a
boundary that re-runs all 24 gate codes fresh. The workflow still does not
journal a send of its own — a second dispatcher on one attempt row would race
the first for the `reserved → requesting` flip and add nothing — but it does
now WAIT for the send that approval authorized, through
`internal.inbox.checkApprovedSend`, a pure read of the `sendAttempts` rows for
the approved revision. It issues no provider request, starts no dispatch and
takes no decision; it reads state and reports it. The mission stays
non-terminal while the send is parked or uncertain, which is what keeps the
send boundary's own gates passing.

**No second approval path exists.** `createRevision` opens
`askKey: draft_approval:<draftId>` through `internal.decisions.openRequiredDecision`
— the same row `decisions.listOpen`, `/decisions` and `/decisions/$decisionId`
already render at `4d2289a`, and the same row `approvals.approve/requestChanges/
reject` already resolve. Nothing in the reply path calls `decisions.resolve`,
which refuses `draft_approval` and `delivery_uncertain` by design.

`installReplyDraft` **reads the ask back and halts loudly when it is absent.**
`drafts.openDraftApprovalDecision` returns silently when a mission has no
dispatched workflow, which would otherwise leave a draft nobody can ever approve
and a workflow waiting on an event nobody will ever send. That is the single
most likely way to ship a reply path that compiles and looks fine, and it is
guarded rather than assumed.

## The ordering rule, and why it is provable

Inside `internal.inbox.applyInboundMessage`, all of this is **one Convex
transaction** (`ctx.runMutation` from a mutation is a sub-transaction of it):

| # | Step | Owner |
|---|---|---|
| 0 | Match `(inboxRef, providerThreadRef)` — `.collect()` + workspace filter, earliest `_creationTime` wins | `matchConversation` |
| 0b | No match → create the unassigned row under takeover + one `system` note | `internal.conversations.ensureUnassignedConversation` |
| 0c | **Refuse a receipt older than the inbound the conversation already carries** — settle `handled` with `late_inbound_superseded` and apply nothing | `applyInboundMessage` |
| **1** | **contextVersion + 1, supersede every open `draft_approval`, cancel every `reserved` attempt** | `internal.drafts.applyInboundContext` — called, not reimplemented |
| 2 | `lastInboundFrom`, as data — written for the message just applied whatever its `From` said, so it always describes the message `lastInboundMessageRef` names | `applyToConversation` |
| 3 | Opt-out: verified explicit → `recordSuppression` for the mailed address **and** the address `resolveOutboundRecipient` would mail next when they differ; ambiguous or unverified-sender explicit → takeover hold, **no** suppression | `enforceOptOut` |
| 4 | The reply gate (14 block codes, reusing P10's `matchSuppression`) | `evaluateReplyAutomation` |
| **5** | **The dispatch point — the reply mission and its workflow** | `startReplyMission` |
| 6 | Receipt → `handled`, or `failed` with a bounded reason | `settleReceipt` |

Step 5 cannot commit unless step 1 committed with it. Four independent reasons
no model token can be spent against a stale approval:

1. The only route to model work is `internal.workerOperations.dispatchWorkerRequest`,
   which refuses a mission with no `workflowId`; the mission does not exist until
   step 5.
2. `start(..., { startAsync: true })` **enqueues**. Verified in source at
   `node_modules/@convex-dev/workflow/dist/component/workflow.js:41-50`: with
   `startAsync` it calls `workpool.enqueueMutation(...)`; **without** it, it calls
   `ctx.runMutation(args.workflowHandle, …)` — which would run the first handler
   poll inside the caller's transaction. The ordering proof rests on this
   difference and it is checked, not assumed.
3. An approval attempted between the bump and the start hits
   `approvals.resolveDraftDecision`, which re-checks that the ask is still open
   **and** that `conversation.contextVersion === draft.basedOnContextVersion`.
4. Even a pre-existing `approved` row cannot dispatch: `sending.currentApproval`
   matches only an approval whose `draftRevision`, `payloadHash`,
   `normalizedRecipient` **and** `contextVersion` all still equal the live values.

And the workflow's own stages re-run the full gate before each dispatch, so a
takeover, close, pause, campaign stop or suppression that lands while the
workflow sits in the queue halts it before it spends anything.

## Application-effect dedupe

Stable key `incoming:<inboxRef>:<providerMessageRef>` (`inboundApplicationKey`),
stored in `emailEventReceipts.applicationKey`, enforced by
`by_workspaceId_and_applicationKey` inside `recordReceipt` — it keys the
**message**, not the event, exactly as §4.3 mandates.

| Case | What stops it |
|---|---|
| Same `event_id` twice | The component's `by_eventId` ledger returns before enqueueing any callback. Zero effects. |
| Same message, **new** `event_id` | `by_providerEventId` misses; `by_workspaceId_and_applicationKey.first()` hits → row inserted already `handled` with `error: "duplicate_application_key"`; the callback returns **before** scheduling. Second belt: a stray schedule hits `handlingState !== "pending"` → `skipped`. |
| Reordered A → B → A′ | A′ caught by the application key. This matters because `applyInboundContext`'s own guard compares only against the LAST applied message and would bump `contextVersion` a second time for A. |
| Reordered delivery events | `applyReceiptToAttempt` now advances `lastEventType`/`lastEventAt` only when `eventAt >= existing.lastEventAt`, and writes each per-type stamp only when absent. P05 **observed** `message.delivered` arriving before `message.sent` in the wild. |
| Late older inbound (drain re-drive) | `applyInboundContext` clamps `lastMessageAt` to `max(existing, at)`, **and** `applyInboundMessage` refuses the receipt outright when `receipt.receivedAt < conversation.lastInboundAt`, settling it `handled` with `late_inbound_superseded`. The clamp alone protected only inbox ordering; `lastInboundMessageRef`, `lastInboundAt`, the `contextVersion` bump and the reply dispatch were all unguarded, so replaying A behind an applied B rewound the thread, superseded B's open ask and started a second mission that stranded B's at `superseded_by_newer_inbound`. |
| Lost callback schedule | `inbound-receipt-drain` (5 min, older than 2 min, ≤50 rows) over the EXACT range `by_direction_and_handlingState_and_receivedAt` on `direction: "inbound"`. Workpool does not retry mutations and the component will not re-dispatch an ingested `event_id`, so a drain is the recovery path, not a nicety — which is why the filter had to move inside the index range: the outbound half never settles unless a send attempt claims it, so ~200 permanently-pending outbound rows would have filled an oldest-first page taken on `handlingState` alone and killed the sweep silently. |
| Outbound receipts that can never match an attempt | Settled `failed` with `no_matching_send_attempt` by the same sweep, after 24 h and only once the same `by_providerMessageRef` lookup the fold uses has proved no attempt in the workspace carries the reference. |
| Verified event for an inbox no workspace claims | Held in `quarantinedEmailEvents` (provider identifiers only) and replayed through `recordReceipt` + `applyInboundMessage` by `internal.quarantine.replayForInbox`, which `drafts.assignWorkspaceInbox` schedules for the inbox it just assigned. Replay carries the original `receivedAt`, so the late-inbound guard still applies to it. |
| A classification answering a message the thread has moved past | `applyReplyDisposition` takes `messageRef` and, when `conversation.lastInboundMessageRef` differs, records the answer on the mission and writes nothing to the conversation — the same guard `prepareReplyDispatch` and `installReplyDraft` already applied. |
| Two callers reaching one message | The reply mission's `requestId` on `missions.by_workspaceId_and_requestId` — a second gate on the same identity. Ingest and `resume` produce one mission. |

`replyMissionRequestId` is the natural key when it fits `missions.requestId`'s
100-character bound, and `incoming#<48 hex of sha256(natural)>` when it does not.
Both forms are deterministic per message and their prefixes differ, so one
message always maps to exactly one key.

RFC 5322 `in_reply_to`/`references` are **not used at all** — not as authority,
not as a hint. They are attacker-settable to any message id, including another
tenant's.

## D1 — unassigned mail and the Needs-you count (contract note for P13)

**No decision, activity or comment row is ever written for an unassigned
conversation.** `decisionFields.missionId`, `activityEventFields.missionId` and
`missionCommentFields.missionId` are all required `v.id("missions")`; a mission
requires a `campaignId`; a campaign requires an associated lead. An unassigned
conversation therefore has no mission, can carry none of the three, and **cannot
appear in `decisions.listOpen` at all**.

Its lifecycle is recorded on the conversation row (`takeoverReason`,
`takeoverBy`, `takeoverAt`, `state`, `contextVersion`) and in `conversationNotes`
rows with `kind: "system"`, which carry no `missionId`.

`conversations.attentionCounts` is the **one** call both surfaces read — the
`/overview` attention block takes `unassigned` (its own count, never folded into
the decision count) and the sidebar Inbox badge takes `needsAttention`. Two
numbers for one thing would be a defect (`plan/ux.md` §3).

The second bucket is named `openTakeover`, not `takeover`, because it is **not**
the row count of `list({tab: "takeover"})`. That tab ranges over
`by_workspaceId_and_humanTakeover_and_lastMessageAt` and returns every frozen
thread — unassigned ones, which are frozen by construction, and
closed-but-frozen ones — because only that index carries the column the tab
pages by, and post-filtering a page is forbidden by §5. `openTakeover` is the
attention definition and a strict subset. **Contract note for P13: do not render
`openTakeover` as the takeover tab's badge.** They are two different things, and
the field names say which is which.

Both buckets are exact ranges on `by_workspaceId_and_state_and_humanTakeover`
and are **disjoint by construction**: every unassigned thread is under takeover,
so summing the plain takeover index would double-count; scoping the second
bucket to `state: "open"` removes the overlap and also drops closed-but-frozen
threads, which are not attention. Neither range post-filters a truncated page.
Counts cap at `MAX_LIST_LIMIT` (50) and pair with `hasMore`, so the renderer
shows `hasMore ? "50+" : String(count)` and never a computed total — architecture
§5 forbids an exact unlimited counter.

## Opt-out

Exactly two things suppress immediately:

1. An **authenticated provider fact** — `message.bounced` / `message.complained`,
   which `sendAttempts.applyReceiptToAttempt` already turns into `kind: "email"`
   suppressions with `reason: "bounce"` / `"provider"`. Untouched by P11.
2. A **deterministic explicit opt-out sentence** matched by `evaluateOptOutText`
   over whitespace-normalized text, case-insensitively — and only when the
   sender is verified to be the address the thread was mailed to.

Two details decide whether this is correct or a self-inflicted outage:

- The scan runs on the reply's **own** text: `extracted_text` when AgentMail
  supplies it, else `stripQuotedReply(text)`, which cuts at the first quoted
  line (`>`), RFC 3676 signature delimiter (`--`), `… wrote:` attribution,
  `----- Original Message -----`, `--- Forwarded message ---`, or Outlook's
  `__________` rule. Without this, every reply quoting **our own outbound
  footer** would suppress the recipient we just mailed.
- An inbound `List-Unsubscribe` header is the *sender's* footer, not a request.
  It never counts as explicit.

Changes from the approved design, made when the design met the real rules:

- `opt out` **alone** is ambiguous, not explicit ("we decided to opt out of the
  conference"). `opt me out` stays explicit.
- `not interested` / `no thanks` are **not** opt-out signals at all. They are
  classifications, and freezing them would take the reply away from the
  classifier that exists to handle them.
- An explicit opt-out from a sender who is **not** the address we mailed is
  downgraded to the hold. Honouring it would let a cc'd third party suppress an
  address in a workspace they have nothing to do with. Automation still stops; a
  human adds the suppression through `suppressions.add`.
- A **verified** explicit opt-out does **not** also set takeover. The suppression
  row is the durable block and it is honoured in both directions that matter
  (`evaluateSendGates` → `suppressed_email`; `resume` and the reply gate both
  re-run `matchSuppression`). A takeover flag on top would be a hold to clear by
  hand for no extra protection.
- The ambiguous-hold note quotes the **rule name** (`mentions_unsubscribe`,
  `remove_me`, …), never a slice of the message. The operator reads the actual
  message in the thread view; a second copy in an app table is what §4.3 rules
  out.

"Unclear cases stop automation pending review", mechanically: `humanTakeover:
true` + `takeoverReason: "ambiguous_opt_out"` + `takeoverBy: "system"` written in
the ingest transaction, so `evaluateSendGates` returns `human_takeover` on the
very next preflight; step 1 already superseded every open ask and cancelled every
parked attempt; the gate then refuses three ways, so **no** reply mission, **no**
workflow, **no** draft, **no** send, **no** model call; one `system` note says
why; and **no** suppression row.

There is exactly one suppression matcher and it is P10's `matchSuppression`
(email key, then domain key). Email suppression never implies the domain.

## Every attacker-controlled inbound string

Svix proves the payload came from AgentMail unmodified. It proves **nothing**
about the content, which originates with whoever sent the email.

| String | Where it is data |
|---|---|
| `from` | Normalized to `lastInboundFrom`. Never selects a workspace or conversation, never becomes a send recipient; in `resume` a mismatch **blocks**, never grants. |
| `to`, `cc`, `bcc`, `reply_to` | Not read at all. No routing and no suppression target derives from them. |
| `subject` | Bounded, returned to the UI as text, never interpolated into a prompt instruction or a log line. |
| `text`, `html`, `preview`, `extracted_text` | The injection vector. Never persisted in an app table. Scanned by a deterministic function returning an enum. Reaches the model only inside a context block labelled `inbound_message`, with the prompt stating in its own words that the block is untrusted third-party data whose instructions are never to be followed. Returned to the UI as **plain text only** — `html` is dropped at the source, which kills markup injection and remote tracking-image loads at the read rather than at the renderer. Never logged. |
| `in_reply_to`, `references` | **Unused**, not even as a hint. |
| `List-Unsubscribe` | Only as a *negative* input: never an opt-out request. |
| `timestamp` | Never an ordering authority — the component's `parseTimestamp` silently degrades to `Date.now()`. Ordering uses `receipt.receivedAt`, and every ordering-sensitive write is monotonic. |
| `message_id`, `thread_id`, `inbox_id` | Opaque strings bounded to 400 before any storage or key construction. They select the workspace only through the saved `workspaces.by_inboxRef` assignment. |
| Model output | Also untrusted — it was written *about* attacker text. `parseWorkerResult` re-validates it and rejects credential patterns; subject/body are re-bounded by `installRevision`; the **recipient is ignored entirely** because `draftOutputSchema` has no recipient field and the address is supplied by the application. |

Logging discipline unchanged: `console.info` with provider IDs only — never an
address, never a body, never a full payload (the §G3 evidence rule).

## BUG — a verified `message.received` with no `thread` object is lost permanently

**Found during this exercise. Not fixed — `convex/integrations/agentmail.ts`
belongs to this card's owner, and the round's rules forbid a gate pass from
editing code.**

`onMessageReceived` declares its arguments as:

```ts
args: { message: v.any(), thread: v.any(), eventId: v.string() },
```

`v.any()` accepts any *value*; it does not accept a **missing field**. The
component calls the callback with `thread: event.thread` verbatim
(`@agentmail/convex@0.1.0` `dist/component/lib.js`, `handleEvent`), and the
component's own `vEvent` declares `thread: v.optional(v.any())` — so a
`message.received` payload with no `thread` object is within the *provider's*
contract and outside *ours*.

Reproduced against the live deployment, on an inbox already assigned to a
workspace, with a conversation already open on the thread:

```
$ …/probe.sh --inbox p11-gate-a@agentmail.invalid --thread p11-thr-1 \
      --message '<p11-m8-nothread@agentmail.invalid>' \
      --event-id evt_p11_m8_nothread --from buyer@example.invalid --no-thread
{"http":204,…}

# deployment log, ~1s later
[CONVEX M(worker:runMutationWrapper)] [ERROR] [Error: ArgumentValidationError:
  Object is missing the required field `thread`. Consider wrapping the field
  validator in `v.optional(...)` if this is expected.
  Validator: v.object({eventId: v.string(), message: v.any(), thread: v.any()})]

# before → after
contextVersion            3          →  3            (unchanged)
lastInboundMessageRef     <p11-m3…>  →  <p11-m3…>    (unchanged)
receipts for <p11-m8…>               →  0
quarantine rows for <p11-m8…>        →  0

$ npx convex run integrations/agentmail:diagnosticInboundState \
    '{"inboxId":"p11-gate-a@agentmail.invalid"}' | grep -c p11-m8-nothread
1        # the component DID store the message and DID mark the event ingested
```

Severity: the reply is lost **permanently and silently**. The endpoint returned
`204`, so the provider will not retry. `@convex-dev/workpool` does not retry
mutations. The component's `by_eventId` ledger means a manual provider resend of
the same `event_id` returns before enqueueing anything. And nothing is left to
replay from: there is no `emailEventReceipts` row for the drain to find and no
`quarantinedEmailEvents` row for `replayForInbox` to release — the message
exists only inside the component's `inboundMessages`, which no P11 path reads
except through a quarantine or receipt row that does not exist.

This is precisely the failure `convex/quarantine.ts`'s own header docstring says
must not happen, and precisely the rule the brief's addendum states: *"`onEvent`
/ `onMessageReceived` must be total over attacker-shaped input: no throwing
validator."* The validator is the throw.

`onEvent` does not share the defect: its args are `{ event: v.any() }` and the
component always passes `event`.

Shape of the fix, for whoever owns it: make the field optional
(`thread: v.optional(v.any())`) — `onMessageReceived` never reads `thread`, so
nothing downstream changes. A `--no-thread` flag on the probe reproduces it in
one command.

```js
// scripts/p11-sign-inbound.mjs — probe, not a test file (cf. scripts/p10-probe.sh)
/**
 * P11 signed-inbound probe signer.
 *
 * Fabricates ONE AgentMail `message.received` event, signs it the way the
 * provider does (svix, over the exact raw body) and POSTs it to the
 * deployment's `/agentmail/webhook`. AgentMail's webhooks API has no
 * resend/replay endpoint (recorded in plan/evidence/P05.md), so a signed
 * fabricated event is the only way to drive duplicate and out-of-order
 * delivery through the real verification path.
 *
 * Usage:
 *   node sign-inbound.mjs --inbox <inboxRef> --thread <threadId> \
 *        --message <messageId> --from <address> [--subject S] [--text T] \
 *        [--event-id E] [--site https://<deployment>.convex.site]
 *
 * The secret is read from AGENTMAIL_WEBHOOK_SECRET in the environment; it is
 * never printed. Run it against an ISOLATED deployment, or against a shared
 * one only with the integrator's explicit go-ahead — a valid signed event
 * writes real rows.
 *
 * Exercises, by re-running with the same/other arguments:
 *   V16.1 duplicate      — same --event-id twice        → one logical effect
 *   V16.1 same message   — same --message, new --event-id → duplicate_application_key
 *   V16.1 bad signature  — --corrupt                    → HTTP 401, no state
 *   V16.2 unmatched mail — a --thread no conversation owns → unassigned queue
 */
import { createRequire } from "node:module";
import { randomUUID } from "node:crypto";

const require = createRequire(import.meta.url);
// svix ships transitively (1.99.1) and pnpm does NOT hoist it to
// node_modules/svix, so `require("svix")` throws MODULE_NOT_FOUND from here.
// Resolve it out of the store instead — the same library the component's
// verifier uses, so a signature this accepts is one the endpoint accepts.
const REPO = process.env.OPENSQUAD_REPO ?? "/Volumes/main/Code/opensquad";
function loadSvix() {
  try {
    return require("svix");
  } catch {
    const { readdirSync } = require("node:fs");
    const store = `${REPO}/node_modules/.pnpm`;
    const dir = readdirSync(store).find((entry) => entry.startsWith("svix@"));
    if (dir === undefined) {
      throw new Error("svix is not installed");
    }
    return require(`${store}/${dir}/node_modules/svix`);
  }
}
const { Webhook } = loadSvix();

function arg(name, fallback) {
  const i = process.argv.indexOf(`--${name}`);
  return i === -1 ? fallback : process.argv[i + 1];
}
const flag = (name) => process.argv.includes(`--${name}`);

const secret = process.env.AGENTMAIL_WEBHOOK_SECRET;
if (!secret) {
  console.error("AGENTMAIL_WEBHOOK_SECRET is not set");
  process.exit(2);
}

const site = arg("site", process.env.VITE_CONVEX_SITE_URL);
const eventId = arg("event-id", `evt_p11_${randomUUID()}`);
const messageId = arg("message", `<p11-${randomUUID()}@agentmail.to>`);
const payload = {
  event_id: eventId,
  event_type: "message.received",
  timestamp: new Date().toISOString(),
  message: {
    inbox_id: arg("inbox"),
    thread_id: arg("thread"),
    message_id: messageId,
    from: arg("from"),
    to: [arg("inbox")],
    subject: arg("subject", "P11 probe reply"),
    text: arg("text", "Sounds good, can you send times next week?"),
    timestamp: new Date().toISOString(),
  },
};

const body = JSON.stringify(payload);
const svixId = `msg_${randomUUID().replace(/-/g, "").slice(0, 24)}`;
const timestamp = new Date();
let signature = new Webhook(secret).sign(svixId, timestamp, body);
if (flag("corrupt")) {
  // Flip one base64 character so the digest is structurally valid and wrong.
  signature = signature.slice(0, -2) + (signature.endsWith("A") ? "B" : "A");
}

// Self-check: prove the signer produces a signature the provider's own
// verifier accepts before trusting any result from the deployment.
if (!flag("corrupt")) {
  new Webhook(secret).verify(body, {
    "svix-id": svixId,
    "svix-timestamp": String(Math.floor(timestamp.getTime() / 1000)),
    "svix-signature": signature,
  });
}

const response = await fetch(`${site}/agentmail/webhook`, {
  method: "POST",
  headers: {
    "content-type": "application/json",
    "svix-id": svixId,
    "svix-timestamp": String(Math.floor(timestamp.getTime() / 1000)),
    "svix-signature": signature,
  },
  body,
});
// Provider IDs only — never the address, the subject or the body (G3).
console.log(
  JSON.stringify({
    http: response.status,
    eventId,
    messageId,
    threadId: payload.message.thread_id,
    corrupt: flag("corrupt"),
  }),
);
```

## Source-level facts this design rests on (checked, not inferred)

- `start(..., { startAsync: true })` enqueues into the workpool;
  without it, `start` runs the first handler poll inside the caller's
  transaction — `@convex-dev/workflow/dist/component/workflow.js:41-50`.
- The component's `inboundMessages` carries `extractedText`/`text`/`preview`/
  `html`, indexed `by_inbox`, `by_thread`, `by_messageId` — but the exported
  `listInboundMessages` accepts only `{inboxId} | {threadId} | {}`, so there is
  **no by-message accessor** and `by_thread` is **global**. Both read-back sites
  therefore filter rows to the conversation's own `inboxRef` before matching the
  message id, because AgentMail thread ids are per-inbox and could otherwise
  surface a colliding thread from another inbox.
- `dispatchWorkerRequest` throws before any write on every failure path, but the
  reply stages still **pre-check** the runtime connection rather than catching:
  `ctx.runMutation` inside a mutation shares the caller's transaction, so a
  caught throw is not a clean rollback, and a stage that wants to park and retry
  has to ask before it calls. `DISPATCHABLE_RUNTIME_STATES` is exported so the
  pre-check and the dispatch cannot disagree.
- `aggregateMissionOutcome([])` returns `"completed"`, so
  `workflows.steps.completeMission` would flatten every reply disposition to
  `completed`. `internal.inbox.completeReplyMission` states the outcome instead,
  keeping the rest of the terminal contract (retire open asks → validated
  transition → sweep runs).
- `missions.create` refuses `kind: "reply"` by name, so the reply mission is
  built directly. Its frozen `inputSnapshot` is assembled exactly the way
  `missions.create` assembles one, so a reply run records the same provenance as
  an outreach run. `parentMissionId` is set for the first time in this codebase.
